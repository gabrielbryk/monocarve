# Errors and exit codes

## Exit codes

| Code          | Meaning                                                                                                                                                                                                                                                                                                  |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `0`           | Success. Also a bare invocation with no arguments, `--help`, and `--version`.                                                                                                                                                                                                                            |
| `1`           | An expected failure (`MonocarveError`, or one of its subclasses), or a command that ran and reported a negative verdict itself (a failed audit, a blocked apply).                                                                                                                                        |
| `2`           | Degraded assessment: evidence was published, but the workspace only partially qualified (for example an unmatched workspace pattern). Set solely by `setQualificationExitCode` in `src/commands/assessment-outcome.ts`, used by `assess` and `batch split-candidates`. No error class maps to this code. |
| `3`           | The command reached a not-yet-ported seam (`NotYetPortedError`). The message always begins `not yet ported: `.                                                                                                                                                                                           |
| `64`          | Malformed invocation: unknown command or flag, a missing or invalid flag value, or no command at all (`UsageError`, including `ArgumentError` from `src/cli/args.ts`). Flags are validated before any command loads config, so a bad flag never triggers a config load.                                  |
| `70`          | Internal defect: anything outside the taxonomy, reported with its stack and `cause` chain. Throw a plain `Error` only for a broken invariant, and start the message with `invariant:` so a report is recognizable as a bug.                                                                              |
| `130` / `143` | An apply was interrupted by `SIGINT` (130 = 128 + 2) or `SIGTERM` (143 = 128 + 15) while mutating the checkout. See "Interrupted apply" below.                                                                                                                                                           |

Commands can also set `process.exitCode` directly (1 or 2) without throwing; `main()` in `src/cli.ts` returns whatever value the command left there once it resolves.

## Error classes

All error classes descend from `MonocarveError` (itself extending `Error`), except the internal-defect case, which is anything that is _not_ a `MonocarveError`. Every `MonocarveError` may carry an optional `hint`: one actionable next step, printed on its own `hint: <next step>` line under the message. Rendered form: `monocarve: <message>` followed by the hint line when present (`renderUserError` in `src/cli.ts`).

- **`MonocarveError`** (exit 1) — base class for an expected failure or refusal: bad input, bad config, bad repo state, or a refused operation.
  - **`UsageError`** (exit 64) — malformed invocation or bad flag value. `ArgumentError` (`src/cli/args.ts`) is the parser's own subclass; when it is the cause, the owning command's usage line is printed after the message.
  - **`NotYetPortedError`** (exit 3) — a declared stub seam. Message always `not yet ported: <what>`. `grep -rn "not yet ported" src/` is the definitive list of what remains unported (currently the npm and yarn package-manager adapters, and the nx and turbo task-runner adapters).
  - **`ConfigError`** (exit 1) — config missing, unparseable, invalid, or not bindable. The executable-config sandbox (`src/config/snapshot-loader.ts`, `src/config/loading.ts`) prefixes its messages with `ASSESSMENT_CONFIG_UNBOUND:`; see the diagnostic catalogue below.
  - **`PlanValidationError`** (exit 1) — a plan manifest failed structural or semantic validation. Carries an `issues: readonly string[]` list.
  - **`HashMismatchError`** (exit 1) — a hash precondition or result assertion failed during apply/audit. Always fatal, always triggers rollback: the working tree diverged from what the plan was compiled against. Carries `path`, `expected`, and `actual`.
  - **`PreflightError`** (exit 1) — apply refused to run: a guarded branch, a dirty tree, or the wrong baseline commit.
  - **`IoError`** (exit 1) — a path the operator named could not be read or written. This is the residue class: every other class names the _stage_ that could not proceed (an unreadable manifest is `PlanningError`, an unreadable scan report is `ScanError`, an unreadable config is `ConfigError`); `IoError` is for a file no stage owns, typically the report an `--out` path asks the CLI to deliver. Not a `UsageError`, since the usage block answers "how is this command invoked?" and a bad `--out` destination did not raise that question; not an internal defect either, since nothing is broken and naming a different path fixes it.
  - **`InputInventoryError`** (exit 1) — the assessment input inventory drifted, or an input (including a config import) cannot be bound. Carries a `code` (`ASSESSMENT_INPUT_DRIFT` | `ASSESSMENT_INPUT_UNBOUND`) and `paths`. See the diagnostic catalogue below.
  - **Domain errors** (exit 1) — one subclass per stage living next to the stage it belongs to (`PlanningError`, `ScanError`, `EvidenceError`, `PreparerError`, and others).
- **Anything not a `MonocarveError`** (exit 70) — an internal defect. Printed with the full stack and `cause` chain, prefixed by an explanation that this is a defect in monocarve or its environment, not a mistake in the invocation.

Wrapping convention: when rethrowing across a boundary, pass the original error as `cause` (`new XError(message, { cause })`) so the internal-failure report keeps the chain. `toError` in `src/errors.ts` normalizes a non-`Error` thrown value without losing it, wrapping it as an invariant `Error` whose `cause` is the original value.

## Assessment diagnostic codes

These are the stable `ASSESSMENT_*` and workspace/scan diagnostic codes used by `assess` and `batch split-candidates`. They appear both in `--json` output (as `AssessmentDiagnostic.code`) and in error messages; renaming one is a breaking change. The diagnostic union (`AssessmentDiagnosticCode`) lives in `src/assessment/qualification.ts`; the `ASSESSMENT_*` subset is documented on `InputInventoryError` in `src/errors.ts`.

Each diagnostic has a `severity` (`info` | `warning` | `error`) and determines the overall `QualificationStatus`: `qualified`, `allowed-empty`, `degraded`, or `fatal`. A `severity: "error"` diagnostic, or a code in the fatal set below, makes the whole qualification `fatal` (exit 1, nothing published). `WORKSPACE_PATTERN_UNMATCHED` is the sole `degraded` code (exit 2, evidence still published). Fatal always wins over degraded.

| Code                                     | Fatal?                | Meaning                                                                                                                                                                       | What to do                                                                                                                      |
| ---------------------------------------- | --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `WORKSPACE_PATTERN_UNMATCHED`            | No (degraded, exit 2) | A configured workspace glob matched no package.                                                                                                                               | Check the pattern against the actual workspace layout; evidence still publishes with package-dependent conclusions unavailable. |
| `WORKSPACE_GLOB_UNSUPPORTED`             | Yes                   | A workspace glob uses syntax outside the supported dialect (exact paths, one `*` per segment, supported negation).                                                            | Rewrite the pattern to the supported dialect.                                                                                   |
| `WORKSPACE_PATH_UNSAFE`                  | Yes                   | A workspace path would escape the workspace root or is otherwise unsafe.                                                                                                      | Fix the offending path in config.                                                                                               |
| `WORKSPACE_PACKAGE_DUPLICATE`            | Yes                   | Two workspace globs resolved to the same package identity.                                                                                                                    | Remove the duplicate or disambiguate the globs.                                                                                 |
| `WORKSPACE_DISCOVERY_FAILED`             | Yes                   | Workspace package discovery itself failed.                                                                                                                                    | Inspect the reported paths/message; likely a malformed manifest.                                                                |
| `SOURCE_ROOT_MISSING`                    | Yes                   | A configured source root does not exist.                                                                                                                                      | Fix the root in config or restore the missing directory.                                                                        |
| `SOURCE_ROOT_EMPTY`                      | Yes                   | A configured source root exists but has no production files, and `--allow-empty` was not passed.                                                                              | Add files, fix the root, or pass `--allow-empty` if that is expected.                                                           |
| `SCAN_UNEXPECTED_EMPTY_GRAPH`            | Yes                   | The scanner produced an empty graph where one was not expected.                                                                                                               | Investigate the scanner configuration and inputs.                                                                               |
| `SCAN_TSCONFIG_EXCLUDES_PRODUCTION`      | Yes                   | The `tsconfig` in use excludes production sources from the scan.                                                                                                              | Fix the `tsconfig` `include`/`exclude`.                                                                                         |
| `SCAN_CONFIGURATION_EXCLUDES_PRODUCTION` | Yes                   | Scanner configuration excludes production sources.                                                                                                                            | Fix the scanner configuration.                                                                                                  |
| `SCAN_REPORT_MALFORMED`                  | Yes                   | A supplied or captured scan report is not a valid scanner report.                                                                                                             | Regenerate the report, or fix a hand-supplied `--graph` file.                                                                   |
| `ASSESSMENT_INPUT_UNBOUND`               | Yes                   | An input (e.g. a config import) cannot be inventoried or resolved.                                                                                                            | Check the failing path; the config or an import it reaches is unreachable from the inventory boundary.                          |
| `ASSESSMENT_INPUT_UNREADABLE`            | Yes                   | An input, config, or output path could not be read.                                                                                                                           | Fix filesystem permissions or the path itself.                                                                                  |
| `ASSESSMENT_INPUT_MISSING`               | Yes                   | An input named by the inventory does not exist.                                                                                                                               | Restore the missing file, or re-capture the inventory.                                                                          |
| `ASSESSMENT_INPUT_DRIFT`                 | Yes                   | Inputs changed between inventory capture and use.                                                                                                                             | Re-run `assess`; do not reuse a stale inventory against a mutated checkout.                                                     |
| `ASSESSMENT_REPLAY_PROVENANCE_REQUIRED`  | Yes                   | An `--replay` bundle lacks readable provenance (input inventory, raw reports), or a bare `--graph` was passed to a surface that requires a full bundle.                       | Point `--replay` at a complete assessment bundle instead of a bare graph report.                                                |
| `ASSESSMENT_REPLAY_INPUT_MISMATCH`       | Yes                   | The `--replay` bundle was captured from different inputs than the current checkout.                                                                                           | Re-run `assess` live, or replay against the bundle that matches the current commit/inputs.                                      |
| `SPLIT_ANALYSIS_INCOMPLETE`              | Yes                   | A declaration batch (`--file`/`--split-hotspots`) did not complete: a TypeScript diagnostic or an unresolved/unsupported relationship was found in the selected program.      | Fix the reported TypeScript errors, or narrow the batch selection.                                                              |
| `EVIDENCE_DESTINATION_BUSY`              | Yes                   | Another cooperative publisher already holds the evidence-directory lock.                                                                                                      | Wait for the other run to finish, or investigate a stuck process.                                                               |
| `EVIDENCE_RECOVERY_REQUIRED`             | Yes                   | A previous publish was interrupted and left owned staging/backup/recovery residue, or the destination holds suspicious residue this publisher cannot prove ownership of.      | Inspect the evidence directory by hand; do not delete residue you cannot positively identify as this tool's own.                |
| `EVIDENCE_DESTINATION_UNSAFE`            | Yes                   | The evidence destination overlaps an analytical input/discovery root, is the repository root, or otherwise fails the destination safety check.                                | Point `--evidence-dir` at a destination outside every analytical root.                                                          |
| `EVIDENCE_REPLACEMENT_REFUSED`           | Yes                   | `--replace-generated` was required to replace an existing bundle, or the existing directory does not look like a bundle this tool published (e.g. a foreign `manifest.json`). | Pass `--replace-generated` deliberately, or point at an empty/new destination.                                                  |
| `EVIDENCE_BUDGET_EXCEEDED`               | Yes                   | `--max-bytes` was set and the bundle would exceed it.                                                                                                                         | Raise `--max-bytes`, or omit optional full reports (`--full-portfolio`, per-hotspot splits).                                    |

Two additional identifiers are not diagnostic codes but appear in the same documentation space:

- **`ASSESSMENT_CONFIG_UNBOUND`** — a `ConfigError` message _prefix_ (not a member of the diagnostic union), raised when executable config cannot run inside, or escaped, the isolated `bwrap` sandbox. See `docs/assessment.md` for the sandbox boundary.
- **`ASSESSMENT_CONFIG_EXEC_START`** — a stderr sentinel the sandboxed config child process prints immediately before user config code runs; syscall-trace reads after that marker are attributed to the config itself, not to the loader's own setup.

`CORE_ASSESSMENT_ARTIFACTS` (`src/assessment/bundle.ts`) is referenced from the same comment block in `src/errors.ts` but is not a diagnostic code — it is the list of artifact paths every published bundle must carry (`summary.json`, `layers.json`, `hotspots.json`, `portfolio.json`, `backlog.json`, `findings.md`, `input-inventory.json`). See `docs/assessment.md`.

## `--json` failure and diagnostic shape

For **assessment commands** (`assess`, `batch split-candidates`), an expected failure never propagates as a thrown error to `main()`. `handleAssessmentFailure` (`src/commands/assessment-outcome.ts`) catches it and prints a structured outcome document, then sets `process.exitCode = 1`:

```json
{
  "schemaVersion": 1,
  "status": "fatal",
  "exitCode": 1,
  "published": false,
  "overrides": [],
  "diagnostics": [
    { "code": "ASSESSMENT_INPUT_UNREADABLE", "severity": "error", "message": "…", "impact": "No new authoritative assessment bundle was published." }
  ]
}
```

This document is printed as JSON _even without `--json`_, because `print()` (`src/commands/shared.ts`) renders any non-string value as JSON regardless of the flag — `--json` only changes how a successful, otherwise-human-readable report is rendered. A successful `assess` prints the analogous shape with `published: true`, plus `evidenceDirectory` and `totalBytes`.

`BatchAnalysisError` (an incomplete declaration batch) gets its own shape, adding `code: "SPLIT_ANALYSIS_INCOMPLETE"` and the batch's `completed`/`failed` path lists; with `--json` it prints that object, otherwise a human summary headed by the command's failure headline.

For **non-assessment commands**, a thrown `MonocarveError` (or an internal defect) is _not_ rendered as JSON even with `--json` set: it propagates to `main()` in `src/cli.ts`, which prints `renderUserError(error)` (`monocarve: <message>` plus an optional `hint:` line) to stderr as plain text and returns the matching exit code. `--json` only shapes a command's own successful stdout report (for example `config-doctor`'s `{ schema: "config-doctor", schemaVersion: 1, ... }`, or `scan`'s summary object); it does not create a JSON failure envelope for those commands.
